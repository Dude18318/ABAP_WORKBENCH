# Playbook: Specification Driven

Используйте этот маршрут, когда пользователь дает ТЗ, ФС, ТС, Word-документ или просит реализовать задачу по спецификации.

## Цель

Сначала понять требования и риски, затем кодить. Не превращать неоднозначное ТЗ в уверенно выдуманный код.

## Алгоритм

1. Найдите исходную спецификацию и связанные материалы.
2. Составьте краткую карту требований: входы, выходы, проверки, источники данных, UI, сохранение, ошибки.
3. Проверьте противоречия, неполные типы, неизвестные `Z_*` объекты и неясные сценарии.
4. Все вопросы и риски зафиксируйте в `docs/agent-context/required_objects/spec_analysis.md`.
5. Если блокеры критичные, остановитесь и попросите пользователя подтвердить детали.
6. Если блокеры некритичные, продолжайте с явными допущениями и `#TODO_SIGNATURE`.
7. После реализации сверяйте код с чек-листом требований из `spec_analysis.md`.

## Decision Rules

| Если | Тогда |
| --- | --- |
| Неизвестен ключевой источник данных | Остановитесь на анализе и задайте вопрос |
| Неизвестна вторичная подпись/описание поля | Продолжайте с `#TODO_SIGNATURE` и записью в missing signatures |
| Требования конфликтуют | Не кодьте до фиксации вопроса в `spec_analysis.md` |
| ТЗ явно требует CDS/AMDP/нестандартный UI | Следуйте ТЗ, но отметьте отклонение от дефолтного Open SQL |

## Минимальный Формат spec_analysis.md

| ID | Требование/объект | Статус | Вопрос/допущение | Влияние |
| --- | --- | --- | --- | --- |
| Q001 | `Z_TABLE` | open | Неизвестны ключевые поля | Блокирует SELECT |

## Не Делать

* Не начинать кодинг по противоречивому ТЗ.
* Не молчать о предположениях по `Z_*` объектам.
* Не считать демонстрационный `plan.md` текущим ТЗ без явного указания пользователя.
