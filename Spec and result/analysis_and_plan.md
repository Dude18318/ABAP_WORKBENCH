# Анализ спецификации и план выполнения (Спецификация 4175)

## 1. Анализ требований (Карта требований)

- **Входы:** Proxy-структура `Z8Predictions` с таблицей `Z8PredictedDates` (содержит поля `QMNUM` и `LatestEndDate`).
- **Выходы:**
  - Обновление поля `ZZLATESTENDDATE` в сообщении ТОРО (таблица `QMEL`) через BDC-вызов транзакции `IW22`.
  - Вызов ФМ `Z_PM_PDM_NOTIFICATION` для успешно обновленных сообщений.
  - Возврат ошибки в PI (возбуждение исключения), если хотя бы один объект был заблокирован, для инициации повтора.
- **Валидации/Условия:**
  - Проверка TVARV: переменная `YCHECK_4175_APS` = 'X' (включение/выключение).
  - Обработка только если новая дата отличается от текущей в `QMEL-ZZLATESTENDDATE`.
- **Источники данных:**
  - Данные из PI (интеграционный поток).
  - Таблица `QMEL` для проверки текущей даты.
  - Логи BAL (`SLG1`) для проверки предыдущих блокировок.
- **Сохранение / ошибки:**
  - Запись логов в `ZPM_APS / IN_Z8_PRED_DAT` с использованием `zcl_logger`.
  - Статусы логов: 'S' (успех), 'W' (идентичны), 'E' (ошибка транзакции/блокировка).
  - Ошибка блокировки (IM 416) пишется только 1 раз (проверка по истории логов).

## 2. Открытые вопросы и допущения (Spec Analysis)

| ID | Требование / объект | Статус | Вопрос / допущение | Влияние |

| Q002 | Логика повтора и блокировок (п. 1.4.3.4) | open | В ТЗ сказано: *"повторный алгоритм должен работать только по сообщениям, которые были ранее блокированы"*. Если применять это буквально, то новые сообщения из шины обрабатываться не будут. **Допущение:** алгоритм будет пытаться обработать ВСЕ переданные в пакете сообщения. Но если сообщение снова заблокировано, мы не будем писать дублирующий лог об ошибке (проверив историю логов). Доработка самого ФМ остается вне рамок текущего кода (или могу написать пример кода для ФМ отдельно). | Низкое (для класса) |
| Q004 | Чтение логов (mo_dao->read_bal_log_from_db) | open | Упоминается метод `read_bal_log_from_db`. В стандартном `zcl_logger` такого метода нет. **Допущение:** я реализую локальный класс `LCL_DAO` с методом `read_bal_log_from_db`, который будет читать данные из таблиц `BALHDR`/`BALDAT` (или использовать ФМ `BAL_DB_SEARCH`). | Среднее |

## 3. План реализации

1. **Создание Каркаса и DAO**
   - Определение локальных типов и констант (TVARV, сообщения).
   - Создание локального класса `LCL_DAO` для инкапсуляции работы с БД:
     - Чтение TVARV `YCHECK_4175_APS`.
     - Выборка текущих значений `ZZLATESTENDDATE` из `QMEL`.
     - Чтение предыдущих логов для определения блокировок (поиск сообщений IM 416 за вчера и сегодня).
2. **Реализация основной логики (Класс ZCL_APS_Z8_PREDICTED_DATES_I)**
   - Добавление инстанцирования `ZCL_LOGGER` и `LCL_DAO`.
   - Проверка TVARV: если пусто/не 'X', выходим.
   - Фильтрация входных данных: исключение тех, где дата идентична (запись лога 'W').
   - Фильтрация/пометка блокировок: если при повторе объект все еще заблокирован, не пишем лишних логов.
3. **Реализация BDC вызова (IW22)**
   - Использование утилиты `ZCL_BDC` для формирования пакета и вызова транзакции.
   - Обработка возвращаемых сообщений (`lt_messages`).
   - Логирование успеха ('S') или ошибок ('E').
   - Сбор информации о блокировках.
4. **Постобработка**
   - Вызов ФМ `Z_PM_PDM_NOTIFICATION` для успешных сообщений.
   - Сохранение лога (`mo_logger->save_log( )`).
   - Если были блокировки — вызов исключения (Fault) для возврата ошибки в шину PI.
5. **Тестирование / Сверка**
   - Выполнение pre-commit проверок.
   - Сверка написанного кода с требованиями из ТЗ и стандартами Clean ABAP.
