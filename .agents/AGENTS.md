# Сводные Правила Разработки ABAP (SIBUR Project Rules)

Данные правила обязательны для выполнения агентом при написании и модификации любого ABAP-кода в этом репозитории. Правила составлены на основе анализа документов проекта:
1. `Регламент ведения разработок (включая BI) v8.9.docx`
2. `Правила оптимизации.docx`
3. `Оптимизация ABAP v1-2.pdf`
4. `optimization.txt`

---

## 0. Как Применять Эти Правила

Этот файл задает рабочий контекст для AI-агента, а не заменяет инженерное решение разработчика. При конфликте правил применяйте следующий порядок приоритетов:

1. Прямое указание пользователя в текущей задаче.
2. Требования ТЗ/спецификации.
3. Корпоративные правила СИБУР из этого файла.
4. Справочники и примеры из `docs/agent-context/references/`.
5. Общие рекомендации Clean ABAP.

Категории правил:

* **MUST** - обязательные правила. Нарушать только если иначе задача невыполнима; в таком случае явно объяснить причину.
* **SHOULD** - предпочтительный путь. Можно отступить в legacy-коде, если это уменьшает риск и объем изменений.
* **MAY** - допустимый прием или справочный паттерн.

При доработке существующего legacy-кода агент должен сохранять минимальный объем изменений. Не переводите весь отчет на новую архитектуру только потому, что редактируемый фрагмент нарушает идеальный паттерн. Исправляйте root cause в границах задачи и затронутого кода.

Корпоративные соглашения СИБУР имеют приоритет над Clean ABAP там, где они явно конфликтуют. Например, префиксы `lv_`, `lt_`, `ls_`, `ms_`, `mt_` используются намеренно и не считаются нарушением в этом репозитории.

## 1. Общие Требования и Архитектура

* **Версия ABAP**: Разработка ведется для версии **ABAP 7.50**.
* **Специфика HCM**: Для разработок в контуре SAP HCM (кадры, орг.менеджмент, расчет зарплаты и т.д.) обязательно руководствуйтесь специализированными правилами, описанными в [Справочнике по разработке SAP HCM (hcm-development.md)](../docs/agent-context/hcm-development.md). Для других функциональных направлений (SD, MM, PM, FI) данные правила не применяются.
* **Разделение слоев (Separation of Concerns)**:
  * Разделяйте получение данных, бизнес-логику, UI/вывод и сохранение.
  * **Main Application Class (`lcl_app`/`lcl_main`)**: Владеет сценарием (use case flow). Вызывает DAO для данных, строит таблицы, вызывает View.
  * **DAO Class (`lif_dao`/`lcl_dao`)**: Изолирует нетестируемые зависимости (`SELECT`, вызовы ФМ, `AUTHORITY-CHECK`, `CALL SCREEN`, запись в БД).
  * **View Class (`lcl_view`)**: Отвечает за ALV/SALV, обработку событий UI.
* **Размещение SQL-запросов**: Все SQL-запросы (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) должны находиться **исключительно** внутри методов DAO-классов. Напрямую в логике приложения (`lcl_app`/`lcl_main`) или представления (`lcl_view`) писать SQL-запросы запрещено.
* **Инклюды (Include Structure)**:
  * `*.prog.abap`: report shell и список include.
  * `*_top`: глобальные типы, константы и данные.
  * `*_s01`: экраны выбора (selection screen).
  * `*_cd*` / `*_ci*`: определения и реализации локальных классов.
  * `*_f01`: процедурные подпрограммы (FORMs, если требуют старые SAP API).
  * `*_evt`: блоки событий (`INITIALIZATION`, `START-OF-SELECTION`) с делегированием в application class.
  * `*_tst` или `*_ut01`: ABAP Unit тесты.
* **Экран выбора**: Для разбора параметров используйте `cl_reca_ranges=>analyse_selection_screen` и маппинг в единую структуру состояния экрана в Main Class.
* **CDS-представления и AMDP**: Создание CDS Views и AMDP (ABAP Managed Database Procedures) допускается **только при наличии прямого требования в ТЗ**. По умолчанию вся работа с базой данных строится на стандартном Open SQL.
* **Использование утилитарных классов**: Если задача может быть решена с помощью существующих утилитарных классов проекта (например, массовое чтение текстов, отправка писем, BDC-вызовы и т.д.), агент **обязан в первую очередь использовать их**. Разрабатывать собственные аналоги или альтернативные обходные пути (workarounds) допускается только тогда, когда стандартные утилитарные классы не позволяют реализовать требуемое поведение. Список утилитарных классов и сценарии их использования описаны в [README.md](../docs/agent-context/references/utility_classes/Памятка_по_утилитам.md). При необходимости (например, для разбора сложных нюансов логики) допускается анализ полного кода утилитарных классов в подпапке [full_code/](../docs/agent-context/references/utility_classes/full_code/), но это следует делать только при реальной необходимости, чтобы экономить контекст.

## 2. Соглашения по Именованию (Naming Conventions)

Используйте единую структуру для переменных в коде: **`[Область_видимости][Назначение]_<Имя>`**

### 2.1. Локальные переменные и параметры
* **Область видимости (1-й символ)**:
  * `g` (Global) — Глобальный объект (только в TOP-инклюде).
  * `l` (Local) — Локальный объект.
  * `i` (Importing) — Входной параметр метода или подпрограммы.
  * `e` (Exporting) — Выходной параметр.
  * `c` (Changing) — Изменяемый параметр.
  * `r` (Returning) — Возвращаемый параметр метода.
  * `m` (Member) — Атрибут экземпляра класса.
* **Назначение (2-й символ)**:
  * `v` (Variable) — Простая переменная.
  * `c` (Constant) — Константа.
  * `s` (Structure) — Структура.
  * `t` / `ts` / `th` (Table / Sorted / Hashed) — Внутренняя таблица.
  * `p` (Parameter) — Параметр экрана выбора (начинается с `p_`).
  * `r` (Range / Select-option) — Диапазон (экранные начинаются с `s_`).
  * `o` / `ref` (Object / Reference) — Ссылка/объект.
  * `ty` (Type) — Локальный тип данных.

### 2.2. Объекты Репозитория и Словаря (DDIC)
* **Пакеты (с 2021 г.)**: `Z<Направление>_<DEV/IF/EX>_<Номер_разработки>_<Краткое_имя>` (например, `ZPIM_DEV_3100_VA05`).
* **Таблицы / Структуры / Типы таблиц**: `ZT<Name(10)>` / `ZS<Name>` / `Z_T<Name(10)>`.
* **Домены / Элементы данных**: `ZD<Name>` / `ZE<Name>`.
* **Классы / Интерфейсы**: `ZCL_<Name>` / `ZIF_<Name>`.
* **Методы классов**: Длина имени метода не должна превышать **30 символов** (техническое ограничение ABAP).
* **Исполняемые программы**: `Z_<Name(15)>`.
* **Функциональные модули / RFC**: `Z_<Name>` / `Z_RFC_<Name>`.

## 3. Оптимизация Производительности и База Данных

### 3.1. Запросы Open SQL
* **Запрет SELECT в циклах (SELECT in LOOP)**: Категорически запрещено выполнять любые SQL-запросы (включая `SELECT SINGLE`) внутри циклов `LOOP` или `DO`. Вместо этого соберите ключи во внутреннюю таблицу, выполните один массовый `SELECT ... FOR ALL ENTRIES` за пределами цикла, поместите данные в отсортированную (`SORTED TABLE`) или хэшированную (`HASHED TABLE`) внутреннюю таблицу, и в цикле производите чтение через `READ TABLE ... WITH KEY / USING KEY`.
* **Выборка полей**: Избегайте `SELECT *`. Выбирайте только нужные поля. Порядок полей в `SELECT` должен соответствовать порядку полей во внутренней таблице (быстрее на 15–20%, чем `INTO CORRESPONDING FIELDS`).
* **Условия WHERE**:
  * Фильтруйте данные максимально на уровне БД с использованием индексов. Порядок полей в WHERE должен соответствовать порядку полей в подходящем индексе.
  * Избегайте отрицаний (`NOT`, `<>`) в WHERE — они отключают индексы СУБД. Используйте `IN` или положительные сравнения.
* **FOR ALL ENTRIES (FAE)**:
  * **Обязательно** делайте проверку `IF lt_table IS NOT INITIAL` перед запросом с FAE.
  * **Запрещено** использовать оператор `OR` по ключевым полям в условиях FAE. Это снижает скорость выборки до 23 раз. Разделяйте запрос на два независимых SELECT или перестраивайте драйвер-таблицу.
* **Проверка существования**: Вместо `SELECT SINGLE` или `COUNT(*)` используйте `SELECT ... UP TO 1 ROWS` с конкретным полем (это быстрее и проходит SLIN проверки).
* **Массовые ФМ вместо точечных**:
  * Избегайте вызова `READ_TEXT` в цикле. Соберите ключи и используйте специализированный утилитарный класс [ZCL_READ_MULTIPLE_TEXTS](../docs/agent-context/references/utility_classes/zcl_read_multiple_texts.abap) для массового чтения текстов.
  * Избегайте вызова `STATUS_TEXT_EDIT` в цикле. Используйте `STATUS_READ_MULTI` или комбинацию `STATUS_PRE_READ_DATA` + `STATUS_BUFFER_FILL_EXT`.

### 3.2. Обработка данных в оперативной памяти (Internal Tables)
* **Типизация таблиц**: Правильно выбирайте тип внутренней таблицы в зависимости от объема данных:
  * **STANDARD TABLE**: Маленькие таблицы (<100 записей).
  * **SORTED TABLE**: Большие таблицы, часто читаемые по ключу или регулярно изменяемые. Дает логарифмический поиск $O(\log N)$.
  * **HASHED TABLE**: Большие таблицы, заполняемые однократно, с поиском только по полному ключу ($O(1)$).
  * *Внимание*: Не используйте операции сравнения (`<=`, `>=`) и неполные ключи для HASHED таблиц — это приводит к линейному поиску и падению скорости до 900 раз. Всегда указывайте ключ явно (`USING KEY`).
* **Ключи возвращаемых таблиц (Returning Parameters)**: Если табличный тип создается исключительно для использования в качестве возвращаемого параметра метода (`RETURNING`), по умолчанию определяйте его с пустым ключом (`WITH EMPTY KEY`). Дополнительные ключи (сортированные или уникальные) добавляйте только при явной необходимости оптимизации поиска.
* **Итерация и изменение (FIELD-SYMBOLS)**:
  * Всегда используйте `LOOP AT lt_table ASSIGNING <fs>` вместо `INTO wa` (быстрее до 9 раз).
  * При изменении полей строки меняйте их напрямую через `<fs>-field = ...` без вызова `MODIFY lt_table` (ускорение до 16 раз).
  * Избегайте вызовов `PERFORM` внутри циклов на больших объемах данных. Инлайньте простую логику (вызовы подпрограмм создают огромные накладные расходы).
* **Поиск (BINARY SEARCH)**:
  * Использование `BINARY SEARCH` без предварительной сортировки (`SORT`) запрещено.
  * В настройках SAP Debugger обязательно включайте проверку сортировки для `BINARY SEARCH`, чтобы при ошибке происходил дамп, а не скрытый возврат `sy-subrc = 8`.
  * Для слияния отсортированных таблиц используйте алгоритм **параллельного курсора** (это самый быстрый метод).
* **Удаление данных**:
  * Не удаляйте строки в цикле `LOOP` по одной (особенно через `DELETE ... WHERE`).
  * Для массового удаления пометьте записи (например, флагом `bwtar = 'XXX'`) и удалите одной операцией `DELETE lt_table WHERE bwtar = 'XXX'` (ускорение до 16 раз).
  * Избегайте `DELETE lt_table WHERE NOT (...)` и `DELETE ... WHERE IN Range` — это работает крайне медленно. Для диапазонов отсортированных таблиц используйте `DELETE lt_table FROM idx1 TO idx2`.
* **Очистка памяти**:
  * Освобождайте память больших таблиц через `FREE lt_table`, когда данные больше не нужны (это возвращает память ОС, в отличие от `CLEAR`/`REFRESH`).
  * Во внутренних таблицах используйте домены типа `string`, а не `char255`.
  * При выходе с экрана ALV (кнопка `BACK`/`EXIT`) всегда очищайте отображаемую таблицу (`CLEAR gt_disp_data[]`) перед `LEAVE SCREEN`, чтобы предотвратить двойной расход памяти скрытой ALV-сессией.
* **Вложенные циклы**: Избегайте вложенных LOOP-циклов без явного указания ключей. Используйте `SORTED KEY` для внутренней таблицы и `LOOP AT ... USING KEY key WHERE ...`.
* **Кэширование**: Если метод или ФМ многократно вызывается в цикле с одинаковыми входными данными (например, чтение описаний структур через `DDIF_FIELDINFO_GET`), реализуйте локальное кэширование результатов (например, в статической хэш-таблице).

### 3.3. Фиксация изменений (COMMIT WORK)
* Не вызывайте `COMMIT WORK` на каждую запись при массовой вставке.
* Выполняйте `COMMIT WORK` пакетами по **200–1000 записей** (1–3% от общего объема).
* Для асинхронных BAPI используйте цикл блокировок `ENQUEUE_*` для подтверждения фактической записи в БД перед чтением.

## 4. Логирование и Обработка Ошибок

* **Логгер**: Используйте `zcl_logger` в качестве проектного фасада. Прямые вызовы Application Log (BAL-функций) в бизнес-логике запрещены (только в DAO/helpers).
* **Сообщения `sy-msg`**: Перед записью в лог делайте фиктивный вывод: `MESSAGE ... INTO lv_dummy`, затем вызывайте `mo_logger->add_syst_msg( is_syst = sy )`.
* **Валидация**: Собирайте ошибки валидации в таблицу `bapiret2_t` и передавайте ее в логгер одной командой `mo_logger->add_bapiret( im_ret = lt_bapiret )`.

* **Исключения и ссылки**:
  * Не перехватывайте `cx_root` без дальнейшей обработки. На границе DAO/Application class ловите ожидаемые конкретные исключения, добавляйте понятное сообщение в `bapiret2_t` или `zcl_logger` и завершайте текущий сценарий безопасно.
  * Неожиданные технические исключения не скрывайте: передайте их вызывающему уровню или залогируйте с контекстом и прекратите операцию. Нельзя продолжать сохранение после технической ошибки.
  * Перед разыменованием ссылок, которые могут быть неинициализированы, проверяйте `IS BOUND`. Для table expressions, где отсутствие строки нормально, используйте `OPTIONAL`/`DEFAULT` или один `READ TABLE ... ASSIGNING`.

## 5. Тестирование (ABAP Unit)

* **Изоляция зависимостей**: Тестируйте бизнес-логику в изоляции от БД, GUI и внешних ФМ с помощью подмены DAO (`lcl_dao_mock INHERITING FROM lcl_dao`).
* **Очистка состояния**: В методах `setup` и `teardown` всегда сбрасывайте состояние синглтонов и глобальных переменных классов, чтобы исключить зависимость тестов друг от друга.
* **ATC проверки**: Не подавляйте предупреждения ATC с помощью прагм и псевдокомментариев (`#EC *`) без обоснования.

## 6. Использование Синтаксиса ABAP 7.50

Разработка ведется строго на версии **ABAP 7.50**. Допускается использование современных конструкций со следующими правилами и ограничениями:

### 6.1. Объявление данных (Inline Declarations)
* **Разрешено**: Использовать `DATA(...)` и `FIELD-SYMBOL(...)` для локальных переменных.
  * Пример: `DATA(lv_date) = sy-datum.`
  * Пример: `LOOP AT lt_table ASSIGNING FIELD-SYMBOL(<ls_row>).`
* **Ограничение**: Избегайте inline-объявлений внутри условий (`IF`/`CASE`), если переменная используется за пределами этого блока, так как область видимости переменной — весь метод/процедура. Это ухудшает читаемость.
* **Ограничение**: При вызове ФМ или методов с обобщенными (generic) типами (`TYPE ANY`, `TYPE TABLE`), не используйте inline-объявления для `IMPORTING`/`RECEIVING` параметров, так как компилятор не сможет корректно вывести тип. Задавайте типы явно.

### 6.2. Выражения с таблицами (Table Expressions)
* **Правило**: При чтении строк таблиц вида `DATA(ls_row) = lt_table[ key = ... ]` **обязательно** предусматривайте обработку случая отсутствия записи. Необработанное исключение приводит к дампу `CX_SY_ITAB_LINE_NOT_FOUND`.
  * **Безопасный вариант 1 (со значением по умолчанию)**:
    `DATA(ls_row) = VALUE #( lt_table[ key = lv_key ] OPTIONAL ).` (или `DEFAULT ls_default`).
  * **Безопасный вариант 2 (проверка существования)**:
    `READ TABLE lt_table ASSIGNING FIELD-SYMBOL(<ls_row>) WITH KEY key = lv_key.
  IF sy-subrc = 0.
    " Используйте <ls_row> без повторного чтения.
  ENDIF.`
* **Внимание**: Для HASHED и SORTED таблиц всегда указывайте ключ явно, если он не первичный: `lt_table[ KEY key_name COMPONENTS ... ]`.

### 6.3. Конструкторы (VALUE, CORRESPONDING, NEW, REF)
* **VALUE**: Используйте для инициализации структур и таблиц: `VALUE #( ( field = 1 ) ( field = 2 ) )`.
* **CORRESPONDING**:
  * Разрешено использовать для простых присвоений структур.
  * **Запрещено** использовать `CORRESPONDING` в циклах по большим таблицам из-за низкой производительности по сравнению с явным присвоением полей.
  * Помните, что `CORRESPONDING #( ... )` заменяет всю структуру. Если нужно скопировать только совпадающие поля с сохранением остальных, используйте `CORRESPONDING #( BASE ( ms_data ) ls_incoming )`.
* **NEW / REF**: Используйте для создания объектов и ссылок: `DATA(lo_app) = NEW lcl_app( )` или `DATA(lr_data) = REF #( ls_data )`.

### 6.4. Условные операторы (COND, SWITCH)
* Разрешено использовать для ветвления логики при присвоении:
  `DATA(lv_status) = COND #( WHEN lv_subrc = 0 THEN 'OK' ELSE 'ERROR' ).`
* В ветке `ELSE` (или последней `WHEN OTHERS`) желательно предусматривать обработку непредвиденных значений (например, выбрасывать исключение или присваивать безопасный дефолт).

### 6.5. Синтаксис Open SQL (ABAP 7.50)
* **Экранирование host-переменных**: Все переменные ABAP в SQL-запросах должны начинаться с символа `@` (например, `@lv_status`).
* **Разделители полей**: Поля в списке `SELECT` перечисляются через запятую: `SELECT field1, field2 FROM dbtab INTO TABLE @DATA(lt_data)`.
* **Строгие правила (Strict Mode)**: Если используется хотя бы одна новая синтаксическая конструкция (запятые, `@`, inline-объявления в SELECT, SQL-функции), то весь SELECT-запрос проверяется по строгим правилам ABAP 7.50 (например, `ORDER BY` должен содержать только поля из списка SELECT, все host-переменные должны быть экранированы `@`, `JOIN` должен быть полностью совместим и т.д.).
* **SQL-выражения и функции**: Разрешено использовать встроенные функции (например, `CASE`, `CONCAT`, `COALESCE`, `SUBSTRING`) на уровне БД для минимизации постобработки в ABAP.

## 7. Режимы Работы Агента (Модификация vs Greenfield)

Агент адаптирует стратегию разработки в зависимости от типа поставленной задачи:

### 7.1. Режим А: Доработка существующего кода (Refactoring / Bug-fixing)
* **Минимум изменений (Minimal Churn)**: Не переписывайте существующую архитектуру отчета целиком (например, не переводите процедурный legacy-отчёт на ООП/MVC), если это не затребовано в ТЗ явно. Делайте точечные исправления.
* **Сохранение стиля**: Придерживайтесь исходного стиля форматирования, именования и структуры кода, если они не нарушают критические правила производительности СИБУР.
* **Локальная оптимизация**: Если вы редактируете цикл или SQL-запрос, который написан неоптимально, оптимизируйте его только в рамках изменяемого блока кода (не занимайтесь рефакторингом стороннего кода без запроса).
* **Использование точечных инструментов**: Используйте инструменты замены строк (`replace_file_content`), избегайте полной перезаписи существующих файлов.

### 7.2. Режим Б: Разработка с нуля (Greenfield Development)
* **Использование Boilerplate**: Для полноценных новых отчетов начинайте разработку с копирования структуры [Каркаса-шаблона Z-отчета (Boilerplate)](../src/boilerplate/). Для маленьких технических примеров, spike-прототипов и точечных правок допускается более компактная структура, если пользователь не просил полноценный отчет.
* **Строгий MVC**: Разделяйте код по 7 инклюдам (`top`, `s01`, `cd01`, `ci01`, `evt`, `tst`, `prog`).
* **Мокирование БД**: Обязательно выделяйте выборку данных в DAO класс и пишите ABAP Unit тесты с использованием заглушки (`lcl_dao_mock`).
* **Современный синтаксис**: Используйте все возможности ABAP 7.50 согласно правилам раздела 6.

### 7.3. Запрос Недостающих Сигнатур (Z-объекты)
* **Проверка наличия**: Если в процессе разработки требуется Z-объект (таблица, класс, ФМ), сигнатуры которого нет в папке `docs/agent-context/references/`, пишите код на основе логически предполагаемой структуры (не блокируя разработку).
* **Специальный комментарий**: В коде рядом с вызовом/обращением к этому объекту обязательно оставляйте комментарий вида: `" #TODO_SIGNATURE: Проверить сигнатуру объекта Z_NAME`.
* **Запись в очередь**: Запишите недостающий объект в таблицу файла [missing_signatures.md](../docs/agent-context/required_objects/missing_signatures.md) для последующего предоставления его описания.

### 7.4. Режим В: Разработка по Спецификации (Specification-Driven Development)
* **Анализ спецификации перед кодингом**: При поступлении задачи на разработку по спецификации (ТЗ/ФС/ТС) агент **не начинает писать код сразу**. Первым шагом проводится полный анализ документа на наличие логических противоречий, неполных данных, конфликтов типов или отсутствующих в контексте сигнатур Z-объектов.
* **Создание отчета по анализу**: Все выявленные спорные моменты, противоречия и вопросы агент фиксирует в специальном временном файле [spec_analysis.md](../docs/agent-context/required_objects/spec_analysis.md) в папке `required_objects/`.
* **Остановка на согласование**: После формирования файла анализа агент останавливает свою работу, указывает пользователю на этот файл и ждет комментариев/разрешения противоречий.
* **Переход к реализации**: Только после того как все спорные вопросы закрыты, агент приступает к этапу проектирования и кодинга (используя при необходимости шаблон Boilerplate).
* **Повторная сверка (Verification)**: По окончании кодинга (или по запросу пользователя) агент проводит финальную сверку разработанного кода со спецификацией. Агент составляет чек-лист в конце [spec_analysis.md](../docs/agent-context/required_objects/spec_analysis.md), проверяя покрытие каждого бизнес-требования, правил валидации и обработки ошибок. В случае обнаружения расхождений агент обязан их исправить или подсветить пользователю. Для исключения «шума» от истории текущего чата рекомендуется выполнять эту операцию в изолированном контексте через запуск выделенного субагента `self` (который получит чистый контекст, содержащий только код, спецификацию и задачу на сверку).

## 8. Стандарты Чистого Кода (Clean ABAP для 7.50)

Данные правила адаптированы на основе руководства SAP Clean ABAP с учетом ограничений версии **ABAP 7.50** и приоритета **внутреннего регламента именования СИБУР** (Hungarian notation префиксы сохраняются во всех случаях).

### 8.1. Константы и Магические Значения
* **Избегайте «магических» значений**: Заменяйте литералы константами.
  * Пример: `IF lv_type = cl_abap_typedescr=>typekind_date` вместо `IF lv_type = 'D'`.
* **Осмысленные имена констант**: Имя константы должно отражать её смысл, а не само значение или тип.
  * Плохо: `CONSTANTS lc_90 TYPE mmsta VALUE '90'.`
  * Хорошо: `CONSTANTS lc_status_inactive TYPE mmsta VALUE '90'.`
* **Группировка констант (Замена ENUM)**: Поскольку в версии 7.50 нет встроенного `ENUM`, группируйте связанные константы в структуры:
  ```abap
  CONSTANTS:
    BEGIN OF lc_s_msg_severity,
      warning TYPE symsgty VALUE 'W',
      error   TYPE symsgty VALUE 'E',
    END OF lc_s_msg_severity.
  ```

### 8.2. Работа с Переменными
* **Область видимости inline-переменных**: Не используйте переменные, объявленные через `DATA(...)` или `FIELD-SYMBOL(...)`, за пределами блока (`IF`, `LOOP`, `CASE`), в котором они были объявлены. Если переменная нужна снаружи — объявите её заранее явно.
* **Цели циклов `LOOP AT`**:
  * Исполняйте `ASSIGNING FIELD-SYMBOL(<ls_row>)` для изменения данных или для высокопроизводительных циклов.
  * Исполняйте `INTO DATA(ls_row)` только если вам нужна копия данных для чтения и тип строки не является ссылочным.
  * Избегайте использования ссылок `REFERENCE INTO` в простых циклах, чтобы не усложнять код разыменованием `->*`.

### 8.3. Внутренние Таблицы
* **Отказ от DEFAULT KEY**: При объявлении табличных типов всегда явно указывайте ключи или используйте `WITH EMPTY KEY`, если ключ не требуется. Использование `WITH DEFAULT KEY` запрещено (приводит к ошибкам сортировки и производительности).
* **Вставка данных**: Для отсортированных (`SORTED`) и хэшированных (`HASHED`) таблиц всегда используйте `INSERT ... INTO TABLE ...` вместо `APPEND`. `APPEND` допустим только для `STANDARD` таблиц.
* **Проверка существования записи**: Используйте встроенную функцию `line_exists( lt_table[ ... ] )` вместо вызова `READ TABLE ... TRANSPORTING NO FIELDS` с проверкой `sy-subrc = 0`.
* **Защита от двойного чтения**: Не делайте сначала `line_exists`, а затем сразу `READ TABLE`. Используйте:
  ```abap
  READ TABLE lt_table ASSIGNING FIELD-SYMBOL(<ls_row>) WITH KEY ...
  IF sy-subrc = 0. ... ENDIF.
  " Или с помощью Table Expressions:
  DATA(ls_row) = VALUE #( lt_table[ key = lv_key ] OPTIONAL ).
  IF ls_row IS NOT INITIAL. ... ENDIF.
  ```
* **Фильтрация в LOOP**: Используйте `LOOP AT lt_table ... WHERE ...` вместо проверки условий `IF` внутри цикла.

### 8.4. Условия и Условные Операторы
* **Позитивные условия**: Старайтесь формулировать условия позитивно (без отрицания). Это упрощает чтение.
* **Отрицание IS NOT**: Используйте `IF lv_var IS NOT INITIAL` вместо `IF NOT lv_var IS INITIAL`.
* **Использование XSDBOOL**: Для присвоения булевых результатов используйте функцию `xsdbool`:
  `DATA(lv_is_valid) = xsdbool( lv_subrc = 0 AND lv_val IS NOT INITIAL ).`

### 8.5. Вызовы Методов
* **Сокращение синтаксиса вызовов**:
  * Опускайте ключевое слово `EXPORTING`, если оно является необязательным.
  * Опускайте ключевое слово `RECEIVING` (используйте присвоение `=` или inline-объявление `DATA(...) = ...`).
  * Не используйте self-reference `me->` при обращении к собственным атрибутам или методам класса, за исключением случаев разрешения конфликтов имен.
* **Принцип Fail Fast**: Проверяйте входные параметры в самом начале метода. При ошибке сразу выходите (`RETURN` или вызов исключения), чтобы избежать глубокой вложенности `IF`.

### 8.6. Оформление и Комментарии
* **Символ комментария**: Используйте символ двойной кавычки `"` в начале строки для комментариев вместо звездочки `*`. Такие комментарии сохраняют индентацию (отступы) при автоматическом форматировании.
* **Удаление закомментированного кода**: Не оставляйте старый или неиспользуемый код закомментированным. Удаляйте его (для отслеживания истории изменений используется система контроля версий / транспорты).
* **Запрет ручного версионирования**: Запрещено оставлять в коде метки изменений (например: `* Mod 001 - Begin / End`).
